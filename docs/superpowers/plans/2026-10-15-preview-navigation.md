# Preview navigation and print readiness implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Task1 is implemented and independently approved at `6ebe563`. Task2 is implemented after exact design approval `1f96dbd`; final source review remains required.

**Goal:** Acknowledge only the currently requested preview DOM, and print the document captured by the print action after its own DOM is ready.

**Architecture:** Keep the bounded LatestPreview renderer, original MarkdownRenderer output API and interactive WebView security configuration. Associate each submitted DOM with a generated identity and validate that identity plus document readiness before acknowledging navigation or applying deferred scroll work. Prefer one separately owned print WebView containing one immutable action capture, so interactive navigation and mode changes cannot replace the document being printed.

**Tech stack:** Existing Java 11-compatible app source, Android minSdk 26 WebView/PrintManager, existing JDK17 host extraction and SDK37 compile tools; no new dependencies.

**Spec:** Existing M0 rendering audit and M2 preview work in `docs/ROADMAP.md`, invariants in `AGENTS.md`, rendering/device gates in `docs/RELEASE_GATES.md`, and the bounded investigation assignment. This plan supplements `verification/preview_behavior/PLAN.md`; it does not reopen queue or renderer implementation.

## Review focus

1. A JavaScript response may arrive after another navigation, edit, tab/theme/font/mode change or shutdown. Validate both the returned DOM identity and the current Java-side epoch again at delivery.
2. An old finish callback may trigger a probe of the genuinely current DOM. Accept that DOM only if its embedded identity and `readyState` match; never infer which navigation generated the callback from its URL or callback order.
3. A timer from an earlier accepted page must not clear newer scroll suppression. Scope flag resets, viewport results and deferred work to their owning page/operation.
4. Printing while the render worker is busy, during tab changes, or with a missing/failing service must not print another document or change editing mode. One immutable print capture and explicit cleanup are required.
5. The print framework may use the WebView adapter after `PrintManager.print` returns. Keep the dedicated WebView alive until the reviewed adapter `onFinish` release boundary; do not destroy it immediately after submitting a job.

## Task 2: One captured, readiness-gated print operation (implemented; source review pending)

**Files:** `MainActivity.java` print action/lifecycle methods and narrow print boundary; `verification/preview_navigation/**`. No renderer, save/history, storage or global UI-layout redesign.

**Interfaces:** The approved separate-helper option is implemented as `DocumentPrint` with one process-owned static nested `Operation extends PrintDocumentAdapter`: captured source/title/palette/font/BOM policy, request identity and lifecycle state. Use the same DOM acknowledgment contract as Task1 on an isolated WebView.

**Alternatives assessed:** Gating the interactive WebView can stop premature printing, but its content may change both before and after adapter creation, including later asynchronous framework layout. Locking that view through printing disrupts navigation/editing and still needs lifecycle ownership. A dedicated one-request WebView avoids temporary Write→Read mutation and preserves Focus/modes. It costs one extra captured source, one render/DOM and a print adapter while a print is active; it is bounded, not free and not an Android peak-memory budget. Do not maintain a queue of print documents. A dedicated executor permits one print render to coexist with one interactive render; this increases transient source/renderer/HTML memory and CPU concurrency versus the old shared executor. The extra process thread is lazy-started and process-owned; neither Activity shutdown nor a canceled Future terminates/adjudicates its task.

### Reviewed print framework lifecycle boundary

Root inspected the canonical Android API documentation on2026-10-15: [`PrintDocumentAdapter.onFinish()`](https://developer.android.com/reference/android/print/PrintDocumentAdapter#onFinish()) is called when printing finishes and permits releasing resources on the main thread. [`onLayout`](https://developer.android.com/reference/android/print/PrintDocumentAdapter#onLayout(android.print.PrintAttributes,android.print.PrintAttributes,android.os.CancellationSignal,android.print.PrintDocumentAdapter.LayoutResultCallback,android.os.Bundle)) and [`onWrite`](https://developer.android.com/reference/android/print/PrintDocumentAdapter#onWrite(android.print.PageRange[],android.os.ParcelFileDescriptor,android.os.CancellationSignal,android.print.PrintDocumentAdapter.WriteResultCallback)) specify that no further adapter calls occur until the supplied result callback completes. This documented framework lifecycle, after successful forwarding of delegate `onFinish`, is the approved disposal boundary; it is NOT an inference from generic I/O cancellation, Activity destruction or job status. Package-private callback constructors require forwarding the actual framework callbacks unchanged, not app callback subclasses.

Use one process-wide static operation admission owner (`DocumentPrint.owner`), managed on main with identity-checked transitions, covering capture/render/load/submitted adapter ownership. An Activity recreation cannot admit another print while the prior owner remains. Cancellation/destroy stops new delegate calls and requests known-job cancellation, but does not dispose an exposed view. Missing or throwing delegate `onFinish` conservatively retains the bounded owner/view; do not promise unconditional cleanup. A successful forwarded `onFinish` disposes on main and releases only its own slot, subject also to actual physical-render completion. Test synchronous/reentrant `onFinish` inside PrintManager.print before it returns (including subsequent null return or throw); stale return/finally work cannot resurrect the finished operation or clear a newer global owner. Before exposure, cancellation may dispose the view, but non-interruptible render admission persists until actual worker exit. Worker-exit/admission handoff cannot depend solely on an Activity Handler callback that `onDestroy.removeCallbacksAndMessages` may discard; use process-owned bookkeeping with a surviving delivery path and identity check. Physical and logical ownership are separate throughout.

### Exact worker, deadline and callback ownership

- `DocumentPrint.owner` is claimed before reading/copying editor text. Store one immutable `DocumentPrint.Capture` (String source/title, final Palette, font, BOM flag) and one generated print DOM token. Reject UTF-16 length above8MiB before copying; strict scalar validation happens on the print worker. A second Activity also observes the same process owner and cannot capture/enqueue a second document.
- Set `renderOutstanding` before executor admission; it covers queued work, running work AND the one queued process-main completion. Task entry checks retirement and the monotonic deadline before validation/rendering. Canceled queued tasks still execute that gate and their final process-main handoff; no Future cancellation or Activity shutdown is treated as worker exit. Render finally posts exactly one `renderComplete` through the process Handler, which consumes delivery and clears the physical reservation. Logical cancellation/deadline can clear disposable UI state but cannot admit another capture while `renderOutstanding` remains true. An executor rejection confirms no task admission and clears that reservation on main. Fatal JVM errors and an exiting process main Looper remain outside recovery guarantees.
- The process Handler owns both the fixed30,000ms timer and render delivery. Activity.main.removeCallbacksAndMessages cannot lose either. Use `SystemClock.elapsedRealtime()` for an absolute deadline checked at queued task entry, render delivery, DOM probe result and immediately before exposure; Handler scheduling alone is insufficient. Repeated page/probe callbacks never extend it. Drop canceled worker results rather than retaining useless HTML; release source references after rendering/loading ownership ends. One process callback owns any returned HTML until consumed, preventing canceled-result backlogs.
- Create the isolated WebView only after a valid render delivery on main. Reuse the trusted root metadata wrapper and same base URL/settings; consume all print-view navigation. One print-DOM readiness probe plus a coalesced trigger handles initial about:blank/current completion ordering. Its callback checks operation identity, view identity, exact generated token/complete state, retirement and absolute deadline. The finite deadline handles a lost pre-exposure DOM callback; successful pre-exposure view destruction makes later callbacks inert and releases view/Activity/source references.
- Assign delegate and mark adapter exposure/SUBMITTING before PrintManager.print. If onDestroy/cancel occurs reentrantly before a nonnull PrintJob is returned, the late job receives that operation's once-only cancellation request. A synchronous successful onFinish may already have disposed/released the old owner before print returns; stale return/null/throw/finally must neither resurrect it nor mutate a newer owner. Set onStart/onFinish/cancel/disposal entry flags before calling external code.
- Exposed retirement denies late layout/write via the original callback's cancellation method; catch a throwing callback without issuing any second completion. Active forwarding passes original attrs/Bundle/CancellationSignal/PageRange/FD/result callback objects unchanged. Do not close the FD or replace cancellation listeners. A successful delegate.onFinish is the documented disposal boundary; disposal failure or missing/throwing finish retains process ownership. Activity destruction clears its ability to show messages but cannot force exposed disposal.

Required controlled fixtures include: one owner across two Activities; exact8MiB/over-cap/malformed-surrogate/BOM boundaries; blocked worker with queued print then destroy (entry skips rendering but eventually consumes its handoff); actual running render then timeout/destroy with no new capture until exit/delivery; Activity callback removal while process completion survives; stale render completion beyond absolute deadline queued before delayed timer; repeated page callbacks cannot extend30seconds; successful and throwing callback/delegate/disposal paths; recursive/duplicate onStart/onFinish; null/throw return after exposure; reentrant destroy before job return; synchronous finish followed by admission of a newer owner before the old print call returns. These tests use actual extracted ownership code and real renderer/strict-count paths where relevant; controlled blocking render or platform faults are labeled seams, not Android runtime evidence.
